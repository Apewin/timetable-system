# 终极商用验收测试 01：后端、API、状态完整性与安全边界

## 一、验收结论

**结论：暂不建议以“无附加控制”的方式正式商用（NO-GO）。最高严重度：P1。**

排课、排考试、异步计算、备份恢复、原子写入、求解结果独立校验和 CLI `--apply` 门槛表现稳定；已有自动化测试全部通过，43 门考试的异步求解、取消、超时恢复和并发求解写回保护也通过。

但本轮发现 3 项 P1：

1. 通用实体 CRUD 不要求 `expected_revision`，两个基于同一旧版本的编辑会依次成功，后一次覆盖前一次。
2. 通用实体 CRUD 会持久化不存在的课程、教师和班级引用，使正式状态文件进入不可求解状态。
3. 认证关闭时，应用直接信任请求的 `Host`，伪造为与 `Origin` 一致后写请求成功；在没有反向代理严格 Host 白名单或身份保护时存在 DNS-rebinding 风险。

正式投产前至少应修复前两项数据完整性问题，并确认生产反向代理启用了身份保护、精确 Host 白名单与可信网段限制。

### 5.2 API GET 与安全响应头

```bash
curl -i http://127.0.0.1:4311/api/status
curl http://127.0.0.1:4311/api/auth/status
curl http://127.0.0.1:4311/api/teachers
curl http://127.0.0.1:4311/api/courses
```

证据：200 JSON；响应包含 `nosniff`、`X-Frame-Options: DENY`、CSP、Referrer-Policy、Permissions-Policy；不返回 `Access-Control-Allow-Origin`。

### 5.3 CRUD、非法值、重复与引用中删除

使用 `T_SAME`、`C_MATH`、`TA1` 等脱敏 ID：

- 正常 POST/PUT/DELETE：通过。
- 重复教师 ID：400，状态未新增。
- `max_per_week=-1`：400，状态未新增。
- 删除仍被教师分工、教师资格引用的课程：400，课程保留。
- `GET /api/entity-dependencies/courses/C_MATH`：返回 `teaching_assignment` 与 `teacher_qualification`。
- `DELETE /api/courses/C_MATH?cascade=true`：200，相关分工和资格同步清理。
- PUT/DELETE 不存在 ID：实际为 400 `BACKEND_ERROR`；预期为 404 和稳定业务错误码。

### 5.4 revision 与并发

通用 CRUD 复现：

```http
PUT /api/teachers/T_SAME
Content-Type: application/json

{"name":"并发客户端甲","expected_revision":7}
```

同一个旧版本再提交“并发客户端乙”：两次均 200，最终为乙，且 `expected_revision: 7` 被当作教师业务字段持久化。

对照用例：43 门考试异步求解从 revision 2 开始；求解期间新增教师使状态变为 revision 3。作业最终：

```json
{
  "job_status": "failed",
  "error_code": "STATE_VERSION_CONFLICT",
  "state_revision": 3,
  "prior_result_not_overwritten": true
}
```

说明仓储层具备 revision 能力，但通用 CRUD 路由没有使用。

### 5.5 引用完整性

以下两个请求均实际返回 200 并持久化：

```json
{"id":"T_ORPHAN","can_teach":["COURSE_MISSING"],"available_slots":[],"max_per_day":1,"max_per_week":1}
```

```json
{"id":"TA_ORPHAN","course_id":"COURSE_MISSING","teacher_id":"TEACHER_MISSING","class_ids":["CLASS_MISSING"]}
```

随后 `GET /api/validate-input` 才返回“教师分工引用不存在的课程”。预期是在写入事务中拒绝，不应让损坏状态落盘。

### 5.6 备份、恢复、状态权限与重启

证据：

- 每次写入前均生成 revision 备份，列表只含 ID、revision、时间、大小、状态和计数。
- 错误确认词：400 `BACKUP_CONFIRMATION_REQUIRED`。
- 旧 revision：409 `STATE_VERSION_CONFLICT`。
- 路径型备份 ID：404 `BACKUP_NOT_FOUND`。
- 正确恢复：200，并以新 revision 保存；恢复前当前状态也被备份。
- 权限：状态和审计文件 `-rw-------`，备份目录 `drwx------`。
- 新增脱敏实体后停止并重启 Node 服务，实体仍存在，revision 从 18 保持为 18。

### 5.7 求解进度、成功、取消、超时与异常隔离

43 门脱敏考试计划异步 API：

```http
POST /api/exams/solve
X-Computation-Job: async
Content-Type: application/json

{"expected_revision":1,"max_time_seconds":60}
```

成功链路：HTTP 202，观察到 `running/solver/25%`，最终 `succeeded/100%`；43 sessions，独立 validation 为 true，状态 revision 由 1 变 2。

取消链路：运行时 `DELETE /api/computation-jobs/:id`，最终保持 `cancelled`，revision 仍为 1，未保存考试安排。

异常链路：缺少 revision 的异步作业进入 failed/100%，错误为 `COMPUTATION_FAILED`；后端随后仍正常响应 200。

超时链路：以等待 worker 和 120ms runner timeout 触发 `SOLVER_WORKER_TIMEOUT`；紧接着执行最小有效求解成功，证明超时仅终止子进程，没有污染主服务。

### 5.9 Host、Origin、CORS 与 CSRF

普通跨源写入：

```bash
curl -H 'Origin: http://evil.invalid' \
  -H 'Content-Type: application/json' \
  --data '{...}' http://127.0.0.1:4311/api/teachers
```

实际 403 `ORIGIN_REJECTED`；`Origin: null` 同样 403。

Host 伪造：

```bash
curl -H 'Host: attacker.test:4311' \
  -H 'Origin: http://attacker.test:4311' \
  -H 'Content-Type: application/json' \
  --data '{"id":"T_REBIND",...}' \
  http://127.0.0.1:4311/api/teachers
```

实际 200 并写入。代码仅比较 `origin.host === req.headers.host`，没有可信 Host allowlist；部署模板还配置 `server_name _` 并透传 `$host`。反向代理 Basic Auth 若在真实部署中保持启用可降低风险，但本轮按“应用认证关闭”边界不能视为根治。

### 5.10 请求体、上传与错误码

| 输入 | 实际 |
|---|---|
| 缺失上传文件 | 400 JSON |
| `.txt` 考试时长文件 | 400 JSON |
| 非法 JSON | production 400 HTML |
| JSON 超过 2 MiB | production 413 HTML |
| 上传超过 10 MiB | production 500 HTML |

生产模式不会输出堆栈和本机绝对路径，但解析器/Multer 错误绕过统一 JSON 错误层。前端和 CLI 无法稳定读取错误码，且超大上传被错误归类为服务端故障。

### 5.11 CLI apply gate

```bash
TIMETABLE_API_URL=http://127.0.0.1:4311/api \
node packages/cli/src/cli.mjs request POST /teachers --data '{...}'
```

无 `--apply`：exit 4，`CLI_WRITE_CONFIRMATION_REQUIRED`，revision 18 不变。

加 `--apply`：exit 0，API 成功，revision 18→19。

### 5.12 操作审计

审计记录仅含：`actor`、`id`、`ip`、`method`、`occurred_at`、`path`、`status`。28 条临时记录中未出现 `body`、`payload` 或 fixture 名称；认证关闭时 actor 为 `trusted-lan`。

## 六、缺陷清单

### P0

**未发现。** 证据：完整后端测试 308/308、CLI 25/25、求解进程异常/超时均未导致主服务退出，备份恢复和旧结果保护有效。

### P1-01：通用实体 CRUD 缺少 revision 并发保护

- **复现步骤**：读取 revision 7；两个客户端分别以 revision 7 更新同一教师名称；先后调用 `PUT /api/teachers/T_SAME`。
- **预期**：第一个成功；第二个返回 409 `STATE_VERSION_CONFLICT`。
- **实际**：两次均 200，第二次覆盖第一次；请求中的 `expected_revision` 还被持久化为教师字段。
- **影响**：多人或多标签页同时操作时会静默丢失修改；错误字段会污染正式数据。
- **相关文件/接口**：`packages/backend/src/server.mjs:2892-2953`、`packages/backend/src/state-repository.mjs:59-68`；通用 POST/PUT/DELETE `/api/:entity`。

### P1-02：通用 CRUD 允许持久化孤立外键

- **复现步骤**：新增 `can_teach=[COURSE_MISSING]` 的教师；新增课程、教师、班级均不存在的 `teaching_assignments`。
- **预期**：事务内以 400/422 和明确引用错误拒绝，revision 不变。
- **实际**：均返回 200 并持久化；直到 `/api/validate-input` 才发现错误。
- **影响**：正式状态文件可被正常界面/API 写成不可排课状态；后续求解和导出中断，需人工清理。
- **相关文件/接口**：`packages/backend/src/entity-state.mjs:36-66` 只校验字段形状，未校验引用存在性；`packages/backend/src/server.mjs:2892-2923`。

### P1-03：认证关闭时缺少可信 Host 边界

- **复现步骤**：向 127.0.0.1:4311 发 POST，同时发送 `Host: attacker.test:4311` 与 `Origin: http://attacker.test:4311`。
- **预期**：未知 Host 返回 403/421，写入不发生。
- **实际**：200，实体写入成功。
- **影响**：若服务可被校园终端访问且没有反向代理严格 Host 白名单/身份保护，恶意网页可结合 DNS rebinding 访问内网 API。
- **相关文件/接口**：`packages/backend/src/server.mjs:229-243`；`deploy/nginx-timetable.conf.template:4,27`。
- **部署缓解**：保留反向代理 Basic Auth；将 `server_name _` 改为精确 IP/域名并为未知 Host 建立拒绝 server；限制可信网段。部署缓解不能替代应用修复。

### P2-01：请求解析和上传大小错误不遵循 JSON API 合约

- **复现步骤**：发送非法 JSON、>2 MiB JSON、>10 MiB multipart 文件。
- **预期**：统一 JSON；非法 JSON 400，JSON/文件超限 413；稳定错误码。
- **实际**：production 返回 HTML；超大文件返回 500。
- **影响**：前端只能显示“未知错误/服务异常”，监控误报 5xx，无法区分用户输入与服务故障。
- **相关文件/接口**：`packages/backend/src/server.mjs:152-153,268-280,1120-1125`；所有 JSON 和 multipart API。

### P2-02：通用业务错误被折叠为 400 `BACKEND_ERROR`

- **复现步骤**：PUT/DELETE 不存在实体、重复 ID、引用中删除、专用 API stale write。
- **预期**：404 `ENTITY_NOT_FOUND`、409 `ENTITY_ALREADY_EXISTS` / `ENTITY_IN_USE` / `STATE_VERSION_CONFLICT`、422 校验错误。
- **实际**：均由通用 `reply` 转成 400 `BACKEND_ERROR`；只有备份恢复单独返回正确 409。
- **影响**：调用端难以实施可靠重试、冲突提示和精确用户引导。
- **相关文件/接口**：`packages/backend/src/server.mjs:268-280` 及通用实体 API。

**未发现新的明确 P3 产品缺陷。** pnpm 在 Node 24 下的 `DEP0169` 弃用提示作为依赖升级观察项保留，尚无证据表明来自业务运行路径。

### 5. 剩余缺陷

#### P2-R1：DELETE 和依赖预览的不存在实体未使用稳定 404

- **复现**：

- **影响**：客户端无法稳定区分“对象不存在”和普通输入校验失败；会影响刷新、幂等删除及错误提示，但当前证据未显示数据损坏或越权。
