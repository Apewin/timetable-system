## 1. 验收结论

**结论：本轮不签署商用通过（No-Go for tester 02）。**

原因不是发现了会直接破坏已有课表的 P0/P1 故障，而是：

1. 已确认 1 项 P2 数据完整性缺陷：通用 API 接受“教师不具备该课程授课资格”的教师分工，错误数据会在后续建模或手工排课阶段才暴露。

### P1

### P2-01：教师分工 API 接受无授课资格教师

复现：

1. 新增课程 `C_BAD`：必修、高一、1 节/周。
2. 新增教师 `T_BAD`：`can_teach=[]`。
3. `POST /api/teaching_assignments`，提交 `TA_BAD`，把 `T_BAD` 分配给 `C_BAD` 和 `TC_G10_1`。
4. 预期：写入阶段返回 400，状态不变。
5. 实际：返回 200，分工被接受并写入。
6. 后续打开手工排课/建模时才出现“教师 T_BAD 未配置为可教授 C_BAD（教师分工 TA_BAD）”。

影响：数据管理阶段可以制造无法排课的状态；教务人员会在更晚的步骤才看到错误，定位和回退成本高。求解器没有把错误课表发布出去，因此暂定 P2，而非 P1。

建议：在新增/编辑教师分工的后端事务中同时校验教师、课程、班级存在，教师 `can_teach` 包含课程，班级与课程年级/授课类型一致；失败时拒绝写入并返回字段级错误。UI 限制候选人不能代替后端校验。

### P3-01：状态版本冲突缺少专用 HTTP/错误码

复现：使用旧 `expected_revision` 保存教室列表。系统正确拒绝覆盖，但返回 HTTP 400 和通用 `BACKEND_ERROR`；消息中才包含“预期版本/当前版本”。

影响：数据安全没有受损，但前端、CLI 和自动化无法稳定区分版本冲突与普通参数错误。建议返回 HTTP 409，并保留 `STATE_VERSION_CONFLICT` 机器码。

### 4. 新发现缺陷

#### P1-01：课程分工匹配旧教师模板后未改写教师身份，导出可误发

复现：脱敏状态中的现任教师为“匿名生物教师”，其分工为高一生物；默认模板存在旧页“高一生物原园”。生成“全部教师课表”后，系统把现任教师课时写入该旧页，但页签仍为“高一生物原园”，第 3 行周一至周五仍全部显示“原园”，第 4 行却已写入现任教师的“生物 / 高一教学班”。用 `artifact-tool` 回读确认整份工作簿没有“匿名生物教师”，且无公式错误。

影响：课表内容正确但教师身份错误，教务人员按页签或 Teacher 行分发时会把现任教师课表误发给旧教师；“全部现任教师课表”不能作为生产输出。应在课程分工匹配成功后，将页签/教师姓名区统一改为当前教师，或为当前教师生成新页并省略旧页；并断言每位现任教师 ID/姓名在输出中恰好出现一次。

#### P2-02：复用同一浏览器源时，旧本地手工草稿未与服务端状态对齐

4302 的服务端 `/api/manual-plan` 明确为空，但页面仍恢复旧 `TC_G10_1` 草稿，提示该班级不存在并禁用快速生成；刷新后仍存在。换到全新 4303 浏览器源后问题消失。状态恢复、换学期或替换数据后可能出现同类阻塞，应按学校/状态 revision 校验本地草稿并提供明确的“一键丢弃失效草稿”。

### 5. 最终结论

**本测试域：NO-GO。最高严重度：P1。**

排课求解、资格校验、周上限、计算作业、教室/班级 CRUD 和归档恢复均已取得正向闭环证据；但教师 Excel 存在可导致错误分发的身份标注 P1，属于投入生产前必须修复的输出完整性问题。修复 P1-01 并用“旧模板教师名与现任教师名不一致”的 fixture 重跑导出回读后，本域才可改签 GO。
